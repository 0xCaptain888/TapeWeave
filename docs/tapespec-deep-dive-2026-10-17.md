## 二、再深一层：真正需要解决的不是“有没有测”，而是谁对什么作承诺

TAP-10的同块读取避免一次操作跨块拼接不同状态；但一个固定区块本身就可能位于多文件发布中间。[D6、D7] 因此必须区分：

1. **链状态一致**：返回的是某块真实内容。
2. **文件完整**：内容匹配该块元数据。
3. **发布一致**：交付的受控文件集合属于发布者声明的同一版本。
4. **应用正确**：业务逻辑正确、无恶意行为。

前两项不自动推出第三项，第三项也不推出第四项。TapeSpec只能围绕第三项做一个明确的可选契约，不销售“全站安全认证”。

### 不可回避的可用性取舍

假设V1的HTML和脚本都原地覆盖为V2，清单最后更新：

- 清单尚指V1、文件已部分覆盖时，新访问应拒绝启动发布一致性模式，而不是执行混版。
- 全部文件已变V2、清单仍V1时，仍需拒绝。**清单最后写并不等于零停机或原子发布。**
- 如需减少这个窗口，需要版本化资源路径、保留旧资源、入口/清单切换和明确加载机制；这需要发布器与读取端共同适配，不能只加一个预检按钮。
- 已打开的文档若继续运行V1，必须把后续动态资源请求绑定同一受控版本；仅启动时预检一次、不管后续请求，不足以实现此承诺。
- 若历史数据不可用、旧资源已删除、客户端没缓存，必须如实报告不可读取；不能靠哈希“恢复”文件。

这就是比普通发布检查报告更深的技术问题：**安全失败、可用性、会话生命周期和可追溯性的联合设计。**

## 三、本轮实际做了什么验证

新增可运行文件：`research/tapespec/release_model.py`，仅Python标准库，无网络、钱包和第三方依赖。

运行方式：

```bash
python3 research/tapespec/release_model.py
```

模型构造V1、V2、混版、旧清单、缺清单和未列出的动态请求，输出6个场景并执行9个单元测试。它展示：

- 每个文件符合其“当前元数据”，仍可能不是同一发布；
- 实验性集合校验会拒绝混版，但也会在原地覆盖窗口拒绝新访问；
- 缺少可选清单只能标不支持，不能判基础协议违规；
- 保留完整旧快照能继续重放，但首次访问的旧完整版本仍可通过，**没有自动解决回滚／新鲜度**；
- 一个只检查逐文件哈希的合成弱实现会接受坏夹具，说明测试不能只有全绿正例。

**证据等级：本地合成逻辑模型。**当前元数据是按夹具字节自行生成，故逐文件校验通过是模型设定，不是链上测量。不是实际TapeKit/TapeNow缺陷报告，不是TAP-10实现，不是浏览器运行、部署复现或性能基准。没有证明真实客户端被修复。它的作用是把产品主张变成可以反驳的最小例子。

## 四、深化后的产品：一个发布契约、两侧适配、三类可复核结果

不增加支付、Agent市场、全协议扫描等功能。名称仍用TapeSpec。

### 4.1 一个实验性发布契约

参考#30已有讨论，描述有限文件集合、精确路径、内容标识、入口、能力版本和请求边界。规范路径与签名格式未定前，使用显式实验profile，**不擅自抢占标准路径、TAP编号或颁发兼容认证**。

它约束“哪些字节可以交给一个会话”，不改链的真实状态，不让发布者声明覆盖链上身份。若规范作者已有实现，应贡献和复用而非发明竞争格式。

### 4.2 两侧参考适配

- **发布侧**：根据实际上传事件生成可测试的状态序列，检查删除顺序、保留策略和清单提交；不接管钱包签名、不默认自动发布。
- **读取侧**：在明确选择实验模式时先验证受控集合，约束后续请求；未满足则安全失败。基础模式仍按其原规范运行，不静默切到另一模式。

与ReleaseLens的区别：核心不是观察某个入口并出报告，而是把同一约束嵌入发布侧和读取侧，并验证“没有把不允许的资源交给页面”。若最后只剩检查报告，就退回旧方案，不能说已经升级。

### 4.3 三类证据输出

1. **行为证据**：实际浏览器交付的资源及会话标识、阻止原因，不仅是runner声称通过。
2. **复现证据**：固定代码版本、环境、配置、输入、事件顺序与最小夹具；凭据脱敏，不自动执行导入脚本。
3. **回归证据**：外部实现修复前后同用例结果，以及后续正常发布再次运行记录。

当前三类均未取得。自建两个适配器不等于两个独立项目采用，同一维护者两个项目也不能冒充两组独立需求。

## 五、必须逐项证明的差异，而非笼统宣称护城河

| 攻坚点 | 比现有单端校验多什么 | 当前状态／验收方式 |
|---|---|---|
| 发布中间状态联合测试 | 把上传顺序和读取时机交叉组合 | 只有合成模型；需接实际发布事件与客户端 |
| 页面实际执行边界 | 验证动态请求、导航及版本切换是否仍遵守会话约束 | 未实现；需浏览器观测，不能仅检查manifest |
| 用例期望的可信度 | 同一profile、规范版本和适用条件，由相关维护者复核 | 未获得反馈；实现分歧不是自动判bug的依据 |
| 测试本身的检错力 | 故意削弱pin、集合检查或会话隔离时，针对性用例应失败 | 仅有合成弱实现控制；需在授权隔离环境做实际变异测试 |
| 多项目持续运行 | 同一套件进入不同项目后续变更流程 | 未接入；不能用GitHub星标代替 |

长期竞争力可能来自真实失败用例、适配深度和维护者信任；**都还没有形成，也不专属于我们**。如果只需要给TapeKit或TapeNow补若干测试，贡献补丁可能更合适。为了参赛强留一个独立平台，是反生态的决策。

## 六、大奖所需的最低证据包，比上一版更严格

以下全部是内部投入门槛，不是官方标准或获奖保证。

### G0：先核实是否值得独立做

- 阅读现有核心实现与更多测试，而不是仅本轮抽样；用例级列出已覆盖、缺口与不可见项。
- 获授权后向发布侧和读取侧维护者分别核实问题是否仍存在、发生场景与解决优先级。
- 若大家只需一个小补丁／规范讨论，停止独立产品立项，不制造“基础设施平台”故事。

### G1：联合机制真正成立

- 一个真实多文件X Layer应用的发布与读取链路；真实地址与ABI先核验，所有付费／写链操作另获授权。
- 同一场景在基础模式、实验模式下呈现不同且合理的结果，不错误指控基础实现。
- 除正常V1/V2，还验证中断、删除、动态资源、旧会话、不可用历史状态；每项说明实际环境还是模拟。
- 外部确认至少一个实际工作流故障或回归风险；若只有合成问题，明确不能进入“已帮助生态”叙事。

### G2：生态结果而非自测成绩

- 至少两个独立维护团队运行共同用例，至少一个真实问题得到修复或形成被认可的可执行限制。
- 后续真实变更再次运行，记录发现与未发现、误报、人工处理和适配成本。没有故障检出不能编造节省时间。
- 产品必须比复制现有单测更有用，否则降为贡献项目。

### G3：向评委展示可核验的结果

三分钟：20秒讲一场真实故障 → 40秒重放“文件都正确、页面却混版” → 40秒展示实验模式如何阻止交付及何时暂不可用 → 35秒修复前后同用例 → 25秒两个独立项目后续使用 → 15秒边界与持续维护。总计2分55秒。

没有两项目使用就删去该演示段并披露缺证，不能用Logo代替授权。核心结果应可由第三人复现，而不是只能看视频。

## 七、重新判断“常见、必要、生态价值、大奖”

- **真实需求**：仍然主要来自#30一个发布团队的详细自述；本轮代码观察证实工具复杂度与已有测试，不独立证明故障发生。
- **常见程度**：多文件更新是可反复发生的操作，不等于混版事故高频；需要真实发布次数、暴露窗口与影响记录。当前未知。
- **必要性**：正确交付应用版本很重要，但可由内容寻址资源、固定快照或现有客户端改进解决；TapeSpec本身尚非不可替代。
- **生态价值**：若把已有讨论转成双方实际采用的兼容行为，并消除反复回归，就比单独检查工具更强；只有自测模型则远远不够。
- **大奖潜质**：方向可以继续验证，**目前仍不具备支持“完整开发必有强大奖竞争力”的证据**。弱点包括工具体验不直观、商业路径不强、规范协作依赖高、可能只适合做现有项目贡献。

不再换题来制造进展，也不追加一个90分。下一步最有价值的工作是G0代码覆盖审查与实际适配可行性核验；开发仪表盘不是优先事项。
