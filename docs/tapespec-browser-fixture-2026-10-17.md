# TapeSpec 浏览器深化：会话漂移的夹具复现与反证边界

> **方案入口：**[新的TapeSpec参赛方案](tapespec-entry-plan-2026-10-17.md)将本报告纳入证据底稿，定义待开发的兼容层、MVP与停止门槛；下列夹具结果不等于方案已经实现。

> 访问与实验日期：2026-10-17，America/Los_Angeles。接续[会话边界研究](tapespec-session-boundary-2026-10-17.md)。本轮将原样上游函数置于自编Service Worker夹具，在真实Chrome运行动态脚本与双标签页实验。**不是完整TapeKit客户端、真实RPC、X Layer或线上故障复现，不证明上游违规或存在安全漏洞。**

## 一、这次究竟前进了什么

上一轮只能证明Node隔离环境下函数更新共享句柄。本轮增加：真实Service Worker接管、真实文档、动态`script`加载并执行、同源双标签页，以及HTTP缓存开关对照。

在夹具中，初始文档的版本标记保持V1；当共享句柄到期且替身解析返回V2时，后续动态脚本执行结果为V2。另一个标签页以`tape-reload`导航也能更新共享句柄，随后原标签页执行V2脚本。

这说明**真实浏览器机制没有天然阻止该类跨版本交付**。它仍不证明完整TapeKit会在真实节点上出现相同行为，更不证明用户因此发生损失。首次取得的快照、资源路径、缓存、更新方式和部署版本都需要继续核验。

**当前推荐不变：只优先验证TapeSpec，不批准完整产品开发。**验证目标进一步明确为“发布版本与文档会话边界”，不新增功能方向，也不靠纸面评分宣称大奖实力。

## 二、先寻找已有防护与反证

本轮重新阅读固定TapeKit提交`40994bd65baedbda4df72cb0985031a5f082f606`的以下文件；均于2026-10-17访问。[R1–R4]

### 2.1 已有浏览器测试很强，但所读文件没有这条确定性序列

`sw-gateway/test/e2e.mjs`已有真实Chrome、主网只读、链上声明与实际字节对照、来源隔离、路由回退、CSP、IndexedDB缓存投毒等测试。

该文件会读取可能由站长更新的样例站，并比较浏览器与Node结果；但在所读文件中，没有看到固定V1/V2、控制句柄到期、保持原文档、再请求延迟资源的序列，也没有看到双标签页刷新后核对旧文档资源版本的断言。

**不能把这写成“项目没有相关测试”**：这里只复核一个公开E2E文件，其他文件、分支与内部测试未穷尽；也没有运行上游E2E。本轮夹具不能替代那些安全测试。

### 2.2 响应头与CSP不是发布版本绑定

`serve.js`的`fileResponse`会设置`cache-control: no-cache`、内容哈希、校验标记、身份头与CSP。它有实质安全作用，但：

- `no-cache`不等于`no-store`，更不等于同一文档永远获得同一版本。
- CSP允许同源脚本，不按发布版本选择脚本；来自同源的完整V2不必因版本不同而被阻止。
- 这不意味着CSP或哈希失效：它们解决的不是同一个问题。

本轮夹具只使用同源脚本策略和`no-cache`，**不是原样复制完整`fileResponse`或完整安全策略**。

### 2.3 兼容档是另一条生命周期，不能套用两分钟

`worker.js`的`fromChain`对请求调用`kernel.resolve`，再`openSite(res).get(path)`；它没有使用SW的`sites` Map。

但`kernel.js`的`resolve`有内存缓存和TTL，不能从“每次调用resolve”直接推导“每个请求都取最新块”。源码注释写默认60秒；实际部署配置与实例复用情况未核实。不同边缘实例也不等于同一浏览器会话。[R3、R4]

**本轮没有运行兼容档。**这里仅说明后续适配必须分别验证两条交付路径；SW夹具的120秒结果不能外推至边缘Worker。

## 三、可复现实验及结果

文件：`research/tapespec/browser_session_probe.mjs`。

```bash
node research/tapespec/browser_session_probe.mjs
```

要求本机有Chrome，默认macOS安装路径，可通过`CHROME`指定可执行文件；无需安装npm依赖。脚本用Node原生HTTP、WebSocket/CDP与临时浏览器配置目录；监听`127.0.0.1`随机端口，完成后关闭服务、浏览器并删除配置目录。夹具自身不访问外部URL或RPC，禁用了浏览器后台网络选项，**没有进行网络抓包，不能保证Chrome没有任何后台联网**。不使用用户日常浏览器配置，不使用钱包或密钥。

### 缓存结论必须限制范围

每个场景只在该文档首次动态加载`late.js`。所以缓存开关对照证明的是：本夹具首次晚加载在两种HTTP缓存设置下均可切换；它没有覆盖“已经加载过同URL的模块再次import”、模块映射、预加载、应用缓存或离线缓存。

版本化文件名、内容寻址路径、打包成单文件、完整导航后重新启动应用，都可能消除或降低某些场景影响。若实际站点只使用这些模式，就不能声称问题普遍存在。

## 四、现在能说和不能说什么

**可以说：**

1. 固定真实函数的共享状态更新，在真实浏览器SW夹具中可以让仍保留V1标记的文档执行V2资源。
2. 初次文档快照通过校验，不足以自动约束后续资源的版本；跨标签页共享状态值得作为测试维度。
3. 所读公开E2E文件没有显示这条确定性序列；可向现有测试体系贡献这一类验证，而不是替代它。

**不能说：**

- TapeKit线上已发生混版、存在可利用漏洞或违反TAP-10。
- 真实文件都通过哈希仍发生事故：本轮内核替身没有计算哈希。
- 页面业务已被破坏：本轮仅执行版本哨兵，无真实应用。
- 所有多文件站点、兼容档或其他实现都受影响。
- 加一个clientId Map即可修复；导航身份、SW重启、历史不可用与安全撤销策略仍待设计。

## 五、如何判断它值得贡献，还是值得独立参赛

本轮减少了一个未知：真实浏览器并不会自动阻止夹具中的版本切换。但**生态价值、频率、严重性、独立采用仍未知**。

下一步按证据增益排序，不扩展功能：

1. **完整交付链：**固定上游源码，用受控RPC状态提供可验证的文件、元数据与区块，运行原样kernel＋SW路径。必须核对实际字节、响应身份与执行结果。夹具结果无法代替这一步。
2. **反证优先：**加入内容寻址资源名、单文件、已加载模块及无更新对照；如果现有实践已完整规避，缩小或撤销普遍性主张。
3. **实际影响：**在不接触资产的代表性应用中，验证接口不兼容是否导致具体失败；不能为了制造失败而给两个版本安排不现实的不兼容。
4. **维护者核验：**仅在获授权联系后确认设计意图、支持模式、现实优先级和是否接受补充测试。未联系，不能预写对方认可。
5. **修复与回归：**先考虑贡献现有项目；只有多个独立实现反复需要同一契约、愿意适配并持续使用，才支持TapeSpec作为跨实现产品。

**停止条件：**完整链路不能复现、既有版本策略已充分解决、无实际影响或无采用意愿，则停止将其作为独立大奖主轴。浏览器夹具可保留为研究材料，不转化成无依据的产品宣传。

## 六、对夺奖方向的最新判断

现有强替代品不是空白。新的证据让TapeSpec从抽象共享测试进一步靠近可执行兼容贡献，但离“不可缺少、独特竞争力”仍有距离。

真正可能形成竞争力的是：被独立维护者确认的跨层问题、兼容现有安全边界的修复、以及后续真实变更中的持续回归。**浏览器哨兵实验本身不是壁垒，也不足以说明具有一等奖实力。**

若最终只有一处生命周期修复，做贡献比造平台诚实；若多个实现有相同但不同形态的边界问题，才有理由建立共同契约。现阶段不增加分数、不转选新题、不承诺外部联系、部署或报名。
