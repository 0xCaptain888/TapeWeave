## 最终方案与评选标准自评分

> **2026-10-17 定稿说明：**下文是最终推荐的参赛产品定义，不是产品已开发完成的声明。后续章节保留研究依据与实施细节；若旧措辞更宽，以本节的窄范围为准。官方标准来源及访问日见文末 S1；本轮不声称获得新用户、竞品或链上证据。

### 1. 最终选题：ReleaseLens——X Layer DeWEB 发布一致性验证台

**服务对象：**正在发布、升级 X Layer DeWEB 应用的个人开发者和小团队。

**核心问题：**用户从某个入口打开的内容，是否对应开发者指定的 TapeOut 链上对象及可验证文件版本？两个入口为什么不同？修复后是否恢复一致？

**核心价值：**将散落在链查询、浏览器日志和人工截图中的信息，组织成一份范围明确、可以复现和比较的发布证据。它不保证整个网站可信、安全或可用，也不能仅凭内容差异认定恶意篡改。

**最终 MVP，固定四步：**

1. **确认对象：**支持一种经核验的 X Layer DeWEB 解析路径。用户输入入口，系统尝试解析候选身份并要求确认；解析失败允许输入真实地址／ID，不猜测身份。
2. **核对内容：**对两个经授权访问入口，在指定区块上下文下，检查协议可验证的文件集。建议首版上限 20 个文件／总计 5 MB，具体值以接口和性能验证调整，超出范围明确排除。不同入口采集时间分别记录，不虚称原子快照。
3. **解释问题：**报告区分“身份不一致、可验证文件不一致、访问异常、无法验证”，给出预期依据、实际观察和复现步骤。普通浏览器加载检查只作辅助；动态 API、无哈希文件、外部依赖不混入已验证范围。
4. **修复复测：**保存修复前后两份报告，按同一规则比较；区块／文件集变化与故障修复分开解释。用户能看到已解决、新增和未覆盖问题，而不只是一个总分。

**产品形态：**新建检查、检查过程、问题报告、版本对比四页面；只读链适配器＋隔离浏览器检查器＋规范化报告模块。报告查看前端计划运行在 X Layer DeWEB，浏览器任务在隔离服务运行；实际发布及费用仍需授权。核心资格证据是实际使用的 X Layer TapeOut 数据，不以未来部署承诺代替。

**不纳入参赛 MVP：**发币、NFT 证书、资金托管、自动签名、全链扫描、全浏览器兼容承诺、通用安全审计、标准制定、完整 CI／订阅系统。草案清单只能单独实验，不作为现行标准强制检查。

### 2. 从用户到商业的闭环

- **用户为什么用：**核对一次发布的身份与文件版本，减少跨入口排错的来回沟通。这是待验证的价值假设，不是已经量化的收益。
- **如何触达：**在获得联系与公开发布授权后，向独立 DeWEB 应用作者提供一次获授权检查，展示可复现样例；社区账号仅为潜在渠道，不算合作方。
- **为什么持续使用：**应用升级或入口变化时，复用上一次发布基线。需要真实第二次使用来证明，不能靠产品设计自动推定留存。
- **谁付费／付什么费：**发布负责人或维护团队；先验证一次接入＋后续发布验收服务，再验证按团队／检查额度收费。价格待访谈与成本测量，不强制用户为公开链查询付费。
- **成本约束：**记录每次检查的 RPC 请求、浏览器运行时长、存储和人工支持时间，限制并发、文件规模与保留期。未测成本前不宣称高毛利或可无限扩展。

### 3. 参赛演示及交付承诺边界

**2 分 50 秒演示：**20 秒说明用户及发布问题 → 35 秒确认真实 X Layer 对象 → 40 秒展示一个内容差异及复现 → 35 秒修复复测 → 25 秒展示独立复现／真实反馈 → 15 秒说明商业模式与生态作用。没有真实生产故障时使用明确标注的受控夹具；不得将注入测试说成线上漏洞。

**最终交付目标：**可访问工具、源代码和新增开发清单、真实地址与只读读取说明、规则版本、正例／负例／无法验证例、修复前后报告、隐私与验证边界、≤3 分钟视频。实际用户记录有多少写多少；未完成项必须披露，不因其出现在方案中就算已交付。

**开发次序：**先完成 G0 的接口、竞品与需求验证，再做一个真实对象的纵向闭环，最后扩到两个独立授权对象与真实试用。G0 核心条件失败，就停止该最终选题并重新决策；“最终方案”不意味着忽略反证、必须做到底。

### 4. 按官方四项标准评分

### 5. 最终判断：可执行，但还不是被证实的大奖项目

**我最终推荐 ReleaseLens，而不是普通兼容检查器。它目前是“值得验证的明确方案”，不是“已经有一等奖实力的作品”。**最高奖竞争力的关键不在继续增加页面，而在同时补齐：真实重复需求、可验证的技术差异、竞品对照、独立用户完整使用。沿用下文五项内部投入门槛；它们不是官方要求，也不保证获奖。

若只能实现截图、测速和报告，即使完成度很好，也不应保留本方案的创新与生态评分；若链数据无法支持所承诺的身份／文件绑定，则方案核心不成立，应停止。若实际试用与复现证据成立，再依据已完成版本重新评分，而不预先承诺“做完就能达到 90 分”。

## 一、决策：只做一个产品，不同时押三个方向

**主推 ReleaseLens——面向 X Layer DeWEB 应用的发布验收与回归证据工具。**

一句话：**发布前，知道你的链上应用哪里不能用；升级后，知道哪里变坏了，并让别人能复现。**

它不是通用网页测速、另一个 DeWEB 网关，也不是安全审计平台。核心是把 **TapeOut 链上身份与内容依据、真实访问观察、可重复的用户流程**放进同一份有版本、有范围的发布报告。

我们的参赛策略：做一个小而完整的生态工具，服务正在发布应用的开发者，展示“发现问题 → 修复 → 复测 → 下一次发布继续用”的闭环。**最先证明节省排错时间，再讨论订阅收入；不发行 Token，不靠挖矿收益，不引入资金托管。**

这次确定主推方向，不等于已经验证市场。最关键的待证假设是：开发者是否有重复验收需求，而且现有浏览器／监控工具不足以低成本完成。

## 二、为什么是这个，而不是继续包装旧 Agent

| 研究证据 | 对我们的设计影响 | 不能得出的结论 |
|---|---|---|
| Blonskr 强调服务、用户、付费、回访四个问题 [S3] | 将“发布与升级”作为重复使用触发点，明确收费对象 | 已有付费客户或官方承诺支持 |

| 手机／钱包兼容投诉后出现已修复反馈 [S5、S6] | 做防回归和环境记录，不把历史故障当当前普遍故障 | 现有网关仍然不可用 |

### C. 据此收紧 ReleaseLens：先做一个 TapeOut 专属问题

**修订后的核心任务：对一个已确认版本的 X Layer DeWEB 对象，判断指定入口提供的、纳入验证范围的文件是否与链上可验证依据一致，并指出升级前后的变化。**兼容性检查降为辅助，不再以“测很多浏览器”作为创新卖点。不能验证的动态 API、外部脚本、无哈希文件必须排除并显式展示。

首发只支持一种经过核验的对象解析路径、明确数量上限的文件集和两个访问入口。结果围绕三个问题组织：**是不是预期对象？哪些内容能验证？变更后用户流程还能不能完成？**不能以页面整体哈希强行代替逐文件及动态依赖边界。

四页面保持不变，但优先实现：① 从链接解析并确认对象（手工输入兜底）；② 展示有范围的链依据／入口检查；③ 用普通语言定位一处差异和下一步操作；④ 修复后复测和版本对比。真实钱包自动化、定时监控、CI、团队订阅均不抢占核心开发时间。

**用三个示例检验核心是否成立：**

- 正例：已验证文件与链上依据一致，报告清楚列出验证范围，不宣称全站安全。
- 负例：在获授权夹具中提供旧版本／不同内容，工具能给出预期与实际字节依据；明确“受控注入”，不能说发现生产漏洞。
- 不确定例：哈希缺失、身份无法解析或 RPC 上下文无法固定时，报告无法验证，而非推断被篡改或自动通过。

如当前协议数据无法支持这种绑定，本轮构思的核心创新就没有成立；必须停止该主张并重新选题，不能退回普通网页测速后仍沿用大奖叙事。

### D. 重新比较候选，而不是维护原来的分数

| 候选 | 用户／商业 | 创新 | 生态价值 | 完整体验 | 当前判断 |
|---|---|---|---|---|---|
| ReleaseLens | 有具体问题线索，重复需求未验证 | 专属内容绑定与发布差异尚待技术／竞品验证 | 核心依赖 TapeOut 数据，需证明实际用途 | 小闭环可演示，仍未实现 | **保留为有条件首选，不能称已具备一等奖实力** |
| CircuitLens | 电路作者需求和付费主体未验证 | 现有反例／CE Bot 重叠风险更直接 | 电路使用直接，但“使用直接”不等于“价值更高” | 需把反例变成集成者能行动的建议 | 仅当真实集成者提出差异需求时切换 |
| TapeGuard | 我们有资产，但生态客户需求最缺证据 | 与普通策略 SDK 的差异待证明 | 公开电路复算合理，执行强制在外部 | 资金安全叙事易超出实际能力 | 不能因旧代码最多就恢复第一 |

**当前三者都没有足够实证被判为大奖级。**官方允许工具作品及商业用途说明，因此无需凭空换成游戏或消费应用；但也不能因工具合规，就默认它优于其他方向。后续若发现更强真实用户需求，应重开选题比较，而不是被 ReleaseLens 名称绑住。

### E. 将 G0 从“可开工”提升为“值得争取高排名”的检验

在原 G0 的需求与接口条件之外，增加以下内部决策门槛（不是官方获奖条件）：

1. **用户价值成立：**目标用户提供可追溯实例，确认现有工作流缺口；“愿意试试”不能代替重复需求。
2. **技术差异成立：**实际接口能支持至少一种通用网页监控单独无法完成的链对象／内容判定，并有独立复现方法。
3. **竞争边界成立：**用同一用例对照现有生态工具与通用工具；若没有增量能力或明显减少操作，不保留原创性主张。
4. **体验闭环成立：**用户能理解输出并执行修复，第二轮能识别问题已消除；真实用例和注入测试分别统计。
5. **持续经营可解释：**确定谁负责采购、何时再次使用，以及 RPC／浏览器成本如何限制；不要求立刻收入，但不能只有奖后再想商业模式。

三分钟视频也按官方要求组织：问题与用户 → 核心功能真实演示 → 商业模式 → TapeOut 使用方式。不要拍成漏洞惊吓片或只演示底层调用。**按规则做是必要条件；能否胜出，取决于这些证据的质量及未知的同场作品，而非本报告给出的评分。**

## 三、目标用户、场景与首批验证

### 3.1 只服务一类首发用户

**正在发布或升级 X Layer DeWEB 应用的个人开发者／小团队。**先不同时做面向 NFT 投资者、普通浏览用户和大型企业的产品。

典型情境：开发者改了前端或容器内容，在自己电脑上看起来正常；另一入口、移动环境或错误网络下出现异常。现有截图只能说明“我这里不行”，不能关联同一链身份、内容版本与环境，更难确认下一版是否修好。

### 3.2 首批目标（建议，未联系）

- 找 3–5 个符合场景的团队访谈；优先独立应用作者，其次网关／容器工具维护者。
- 至少 2 个团队提供获授权的测试对象和明确主流程；至少 1 个愿意在第二次发布时重复使用。
- 询问最近一次实际故障、排查时间、已有工具及谁负责上线；不问“你觉得这个想法酷不酷”。
- 肖战羊等账号是潜在访谈入口，不是已确定客户、合作方或评委关系。不擅自使用其 Logo、评价或身份背书。

**继续条件：**至少 2 个团队确认具体重复问题，且能说出报告中哪条信息会改变发布决定。这是我们的投入门槛，不是市场成立的统计证明。

## 四、参赛 MVP：四个页面，一条完整闭环

| 页面／模块 | 必须完成 | 明确不做 |
|---|---|---|
| ① 新建检查 | 输入 X Layer 身份与访问入口，选择主流程、规则版本和测试环境 | 任意链／任意协议扫描 |
| ② 检查过程 | 显示身份解析、文件检查、入口观察与用例执行状态 | 后台偷偷签名、发交易或付费 |
| ③ 问题报告 | 每项给原因、证据、复现步骤和未覆盖范围 | 一个绿色分数冒充全面安全 |
| ④ 版本对比 | 同一对象修复前后差异、解决／新增／未复测问题 | 大型监控平台、全套 CI 与协作系统 |

### 4.1 检查能力分三层，不能相互冒充

**A. 链上依据（核心）**

- 以核验过的 X Layer 部署与 ABI 解析处理器／电路／容器关系，记录 chainId、地址、ID、区块号与区块哈希。
- 查询可用的文件元数据与内容哈希；按确认的算法与规则逐文件验证。仅在协议提供可验证绑定时，确认访问内容与链上对象的关系。
- 若 RPC 不支持历史查询、查询跨区块、缺少哈希或版本不支持，输出明确的限制，不拼成一个虚假的一致快照。
- 草案 #62 的清单检查默认不启用；若启用，标为“实验规则”，不影响稳定规则的合格结论。

**B. 浏览器观察（自动但有限）**

- 一个桌面浏览器环境、一个移动视口，观察加载、资源错误和预先定义的界面断言；每个入口独立执行并记录时间。
- 资源内容经过规范化比较时必须列出被排除项；只验证到部分文件，就不声称验证了全站或动态 API 数据。
- “页面打开了”不等于产品流程成功；移动视口也不等于真实手机、钱包内置浏览器。

**C. 钱包／设备流程（人工记录优先）**

- 提供错误网络、用户拒绝连接、拒绝签名及成功结果定位的操作脚本，由用户在受控环境中运行。
- 记录设备、钱包、版本、步骤和结果，标为“人工记录，未独立认证”。未运行就是未覆盖。
- MVP 不执行主网资金操作。钱包流程不适用的应用明确标记不适用，不强迫每个应用连接钱包。

### 4.2 报告不是证书

单项结果使用：**通过／发现问题／无法验证／未覆盖／不适用**，附证据层级。关键链身份无法验证时，不显示总体“可发布”。可以提示“当前已检查项无阻断问题”，但必须紧邻覆盖范围。

报告最小字段：报告版本、工具版本、规则版本、对象身份、区块上下文、采集时间、入口、环境、用例、观察与预期、结果、证据摘要、复现步骤、限制、前一报告标识。导出 JSON 与可读页面。

报告摘要覆盖上述字段的规范化表示；敏感资料先脱敏，摘要只证明报告字节一致，不证明观察真实。不要复用旧回执中未覆盖全部字段的 Merkle 叶子后声称防篡改完整。原始日志不公开钱包隐私、会话 Token、密钥或无关用户信息。

## 五、TapeOut／X Layer 如何真正进入产品

**必须有的集成：**真实读取 X Layer 上 TapeOut／DeWEB 的身份与内容元数据，并把它用于验收判定。去掉这层后，产品会退化成普通网页检查器——这就是本产品需要 TapeOut 的原因。

**计划采用的交付方式：**公开报告查看前端尽量部署到 X Layer DeWEB；浏览器检查器在独立隔离环境运行。只读链查询与页面报告不需要测试者充值或先连接钱包。容器大小、资源限制、发布方式与成本尚未核验；如果无法承载，则先保持普通访问入口，不能虚称已经 DeWEB 部署。

**规则门槛：**官方文本对“或在 X Layer DeWEB 运行”和使用电路／合约／数据的要求存在表述差异，沿用双满足优先策略。正式投入前核实所选数据集成及部署方式的参赛资格，依据官方当前规则或获得可追溯答复 [S1、S2]。不为凑资格设计无业务用途的门电路。

**无需新增资金合约：**MVP 不上链存每份报告，不发 NFT 证书，不承诺“全链不可篡改审计”；已有链对象和可复现读取已是核心验证对象。可复算不等于无须信任 RPC，报告应展示来源；高价值结果可增加第二 RPC 核对，但不包装成共识证明。

## 六、实现边界与已有资产

建议结构：`web`（表单／报告／差异）→ `coordinator`（任务与配额）→ `chain-adapter`（只读解析）＋ `isolated-runner`（浏览器观察）→ `report-core`（规范化报告）。这是设计建议，尚无这些实现。

| 已有资产（详见原报告 G1、G5） | 可以借用 | 本次必须新增 |
|---|---|---|
| agent-control-plane | 回执展示、任务状态与证据结构的设计 | TapeOut 只读适配、报告字段承诺与版本差异 |
| proof-of-calibration | 负向测试、证据不一致时拒绝的思路 | 页面用例、入口差异、设备记录和故障夹具 |
| 其他旧项目 | 经许可核查后的局部 UI／工程惯例 | 不能将旧部署、交易、用户数算作新产品成果 |

**安全是 MVP 边界，不是后补：**仅测试获授权对象；限制任务并发、超时、下载大小和路径数量。拒绝内网、回环、链路本地及云元数据地址，对 DNS 解析、重定向与页面子资源均执行出站限制；隔离浏览器不挂载秘密、不接真金钱包、不暴露内网；抓取文件不直接执行为服务端代码。报告中的页面截图／HTML 也按不可信内容展示，不在查看器同源执行。

资产观察来自前轮选择性只读代码研究，未重新审计、未运行旧项目测试；开始复用前仍要确认许可证及固定提交。

## 七、商业与增长：把留存放进产品结构

**用户为什么用：**减少发布前漏测，以及“你这里坏、我这里好”的重复沟通。**为什么回来：**每次内容／前端／入口更新后重跑，用同一基线识别回归，而非查看一次后离开。

初期免费提供有限单次检查；收费优先验证“一次接入＋持续发布验收服务”。有重复需求后再做团队历史、定时回归或 CI 集成订阅。**不先设一个看似精确却无人验证的月费。**

首批分发建议：发布一个可读的故障→修复对比样例，提供可复现测试夹具，邀请 3–5 个团队试用；获许可后分享匿名案例和模板。只在得到用户授权后对外发帖、联系账号或提交 GitHub 内容。

记录指标而非刷量：独立试用团队数、完成首份报告数、第二次发布复用数、实际修复问题数、人工复核误报数、完成检查耗时、付费意向与真实支付分开统计。所有数字按真实记录填写；“目标 2 个团队”不能写成“已服务 2 个团队”。
